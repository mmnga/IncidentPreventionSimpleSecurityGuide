# IPA注意喚起を対策チェックへ統合 — v6

原文：https://www.ipa.go.jp/security/security-alert/2026/alert20261009.html

公開日・本文確認日：2026-10-09。特定製品が原因だという断定はない。以下は本スキルの実装・検証設計であり、IPAの公式認証や逐語的チェックリストではない。

## 重複排除の結果

既存220 IDを維持。新規ID 0、既存8項目を強化、36項目へ対応付け、うち28項目は既存条件を再利用した。IPA12テーマはナビゲーションであり、項目数に加算しない。

| ID | 既存項目へ統合した理由 |
|---|---|
| OBS-06 | ログの保持値だけでなく、サービスごとの調査権限と入手可能期間が不足。 |
| OBS-07 | 既存の監査イベントを維持し、アカウント不正追加・再有効化の追跡を明確化。 |
| OBS-09 | 既存の大量取得検知では、直近ログの期間拡張と再調査手順を明示していない。 |
| INT-01 | コード上のconnectorだけでは、部署単位の外部サービスやVPNが抜ける。 |
| INT-04 | 退職時の解除に加え、不正アカウントと停止済みIDの復活を拾う必要がある。 |
| AZ-06 | 一括処理の単件相当認可を、非同期ジョブと取得経路まで具体化する。 |
| WEB-09 | 既存の機能別制限を、利用者入力による件数上書きにも適用する。 |
| IR-01 | 連絡先だけでなく、異常発見をインシデント判断へ進める条件を明確にする。 |

完全な変更前は `ipa-delta.json`、現在の合格条件は `checks.json` を参照。追加6条件と既存2条件の拡張で、全範囲側の個別強化条件は108から114へ変更。

## 追加した静的な候補ルール

| ルール | 統合先 | 判定上の注意 |
|---|---|
| bulk-export-entry | AZ-06 | 一括取得routeのレビュー起点。認可欠如の自動断定ではない。 |
| zero-negative-query-limit | WEB-09 | 0/負数の意味はライブラリごとに確認する。 |
| request-controlled-query-limit | WEB-09 | 上流の型/上限検証があるか追跡する。 |
| account-reactivation | INT-04 | 正常な有効化も検出するため、承認と状態遷移を読む。 |
| whole-record-response | DAT-02 | fieldの必要性とserializerを確認する。 |
| audit-logging-disabled | OBS-07 | 設定キーの製品schemaと対象を確認する。 |
| short-log-retention | OBS-06 | 調査期間と最小化を考慮。一律90日要件ではない。 |
| broad-oauth-scope | INT-02 | 必要性がある場合もあり、業務/APIと照合する。 |
| storage-encryption-disabled | DAT-03 | 製品schemaと代替暗号化・鍵管理を確認する。 |

9ルールを追加し、既存56から65へ。候補対応項目は51から59へ。いずれもREVIEWであり、無検出は合格にならない。汎用字句パターンであり全言語/構文やデータフローを解析するものではない。

## 全範囲と静的スコープ

静的profileは172既存IDのソース・宣言・提供済み静的資料の側面を評価する。48 IDは実環境中心でOUT_OF_SCOPE。どちらも元の220 IDを削除しない。

全範囲の条件を静的な文字列チェックで置き換えず、`static_review` に別の限定条件を置く。staticのREVIEW PASSEDはSTATIC ONLYであり、full_auditはNOT_ASSESSEDのまま。

## 再利用した既存項目

AUT-01, AUT-02, AUT-10, AZ-01, AZ-04, CLD-01, CLD-02, CLD-03, DAT-01, DAT-02, DAT-03, DAT-05, DAT-06, DAT-08, DAT-09, INT-02, INT-10, IR-05, IR-09, RAN-01-03, RAN-01-09, SEC-07, SUP-01, SUP-02, SUP-03, SUP-08, TST-01, WEB-06

これらの原定義を事例名だけで複製していない。特に認証・公開範囲・既知脆弱性・データ最小化・暗号化・保存期限などの既存統制を再利用する。

## 実環境確認として残すもの

実ログの異常調査、正規台帳と実アカウントの突合、MFA例外、実パッチ適用、実データ残留、クラウドの有効設定、監視到達、バックアップ不変性/復元は、コードのレビューだけで完了としない。

ログ調査の期間拡張と保存期間の要件は別。調査可能期間と保持の根拠を整理するが、全システムへ一律90日保持を強制する判定にはしていない。
