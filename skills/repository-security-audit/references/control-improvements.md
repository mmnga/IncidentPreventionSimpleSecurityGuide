# 課金監視・利用者への通知と確認方法

公開・配布する資料は一般化した対策を説明する。個別企業・組織の事故説明、引用、事例記事のURLは含めない。参照資料の扱いは [reference-policy.md](reference-policy.md) に従う。

対応IDと追加条件は [control-update-v9.1.json](control-update-v9.1.json)。既存の220チェックIDを維持し、同じ対策を重複して数えない。

## 既存条件で確認する範囲

| 論点 | 確認先 | 確認内容 |
|---|---|---|
| 公開アプリとバックエンドAPI | SEC-05、AUT-01、AZ-01/02/04、RAN-01-09、TST-01/02 | 公開クライアントから旧APIを含む入口、サーバー側認可まで対応付ける。難読化、WAF、端末識別だけで合格させない |
| 認証情報・クラウドID | SEC-07/08/10、AUT-02、CLD-03 | 要求権限の記述、実際の適用、旧資格情報の拒否結果を分ける |
| 保有データの最小化 | DAT-01/02/05 | 保有目的・期限・削除経路・復元時の扱いを確認する |
| 調査と監視 | OBS-06/07/09、IR-04 | クエリの定義と実ログ調査を分け、対象期間と不足を記録する |

## 追加した条件

既存の個別条件は書き換えず、次を追加した。本スキル独自の具体化であり、外部資料の公式チェックリストではない。

- **WEB-09/S4（静的）、WEB-09/LAC-1（full）**：課金対象APIとクラウドIDを費用・利用量の監視、通知先、停止・失効判断へ結び付ける。AI製品がなくてもクラウドIDからの課金サービス悪用を確認し、非該当には証拠を求める。通知と強制制限を区別する。
- **IR-08/LAC-1（fullのみ）**：確定前後を区別した公表・対象者通知・注意喚起のひな型、承認権限、更新判断を記録で確認する。staticでは引き続きOUT_OF_SCOPEであり、文書の存在だけで合格にしない。期限は適用される条件から判断する。

照合IDは既存の証拠との互換性のために維持する。IDから個別事例の内容を出力しない。

## 確認方法とFAILの意味

レポートの主分類は「静的解析」「動作検証」「実環境の設定・権限確認」「ログ・運用記録の確認」「復旧・対応訓練」。分類は必要な確認方法であり、実施済みの表明ではない。複数の方法が必要な項目は、主分類と詳細の合格条件を合わせて読む。

staticでは172項目の静的な側面のみを判定する。テスト定義を読むこと、Terraformを読むこと、監視ルールを読むことを、それぞれ実行成功、適用済み、実ログ調査済みと表現しない。実環境中心の48項目は合格や非該当に変更しない。

FAILは「証拠付きで合格条件に反する不備が確認された」という結果。修正先はソース・設定・資料・運用に分かれ、個別の根拠と適用条件から説明する。

## 証拠と安全境界

220 ID・static 172・OUT_OF_SCOPE 48、schema 3、状態・終了コード・証拠期限を維持する。v9.1時点の静的個別条件は182、full個別条件は125。現行v9.2は[メールの追加条件](mail-notification-review.md)を含め静的184・full 127。台帳・エンジンが変わるとscopeも変わる。旧scopeを書き換えて証拠を再利用しない。

保存済み結果の表示を更新する場合は旧基準・元の日時と追加条件未確認を明記する。対象コード・実環境・実ログの調査や実行、課金、設定変更、通知は自動実行しない。fullも別途認可された結果の証拠を受け取るだけである。
