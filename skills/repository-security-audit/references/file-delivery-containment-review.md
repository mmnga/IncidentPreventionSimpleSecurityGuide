# ファイル配信・サービス間認証・封じ込めの確認

添付ファイルの公開、画像変換・URL取得proxy、サービス間ログイン、通知配信、侵害対応手順がある場合に読む。既存条件の確認先と必要な証拠を具体化する手順であり、220 ID・静的184/full 127条件や合否基準は追加・変更しない。

## 既存項目への対応

| 確認する境界 | 既存の確認先 | 静的レビューの証拠 |
|---|---|---|
| 公開クライアントから旧版・モバイル・ファイル配信への入口 | RAN-01-09/S1・S2、AUT-01/S1、TST-01/S1・S2 | クライアント参照→route→ingress→認証/認可のファイル・行と未提供経路 |
| ファイル公開から許可root外・設定・ソースへの読取 | INJ-05/S1、REL-01/S1、SEC-01/S1 | IDと保存先の対応、path正規化と実際のopen、配布許可範囲、権限/mount宣言 |
| URL取得処理から内部宛先への到達 | INJ-06/S1 | 呼出元、URL/DNS/redirect/retryの検証、接続先制約とegress宣言 |
| サービス用の鍵から利用者・他サービスの権限への拡大 | INT-08/S1、SEC-07/S1、AUT-01/S1、AUT-04/S1・S2、AUT-10/S1、RAN-01-05/S1 | 発行主体・宛先・用途、利用者認証との区別、失効分岐、制限・IAMの宣言 |
| 通知worker・直接送信経路の濫用 | WEB-09/S5、CLD-03/S1、RAN-01-05/S1、OBS-06/S1、OBS-07/S1、OBS-09/S1・S2 | 送信権限、宛先/本文の由来、迂回経路、共有上限・監視・停止判断の定義 |
| 保全と、その後の隔離・失効・再構築・再開 | IR-05/S1、SEC-10、IR-02、IR-03、IR-06、IR-07 | 静的には保全手順を確認。後半5項目の実施結果はstatic対象外のまま残す |

同じ問題を新しい事例用IDへ重複登録しない。関連する全条件を担当workerが個別に評価し、経路台帳を共有しても各条件の根拠を省略しない。

## ソース・宣言的設定で追うこと

1. **公開入口とファイル取得を結ぶ。** route名を検索するだけでなく、認証、ファイルIDの解決、所有者/tenant認可、pathまたはURLへの変換、読取・応答まで追う。公開が意図されたファイルは、その存在だけでFAILにしない。未提供のhandlerや別repoは未確認に残す。
2. **pathとURLの処理を分けて確認する。** ローカル読取では正規化後の許可root境界、絶対path、symlinkと検証からopenまでの競合処理を読む。ファイルIDをサーバー管理の保存先へ対応付け、公開対象と設定・秘密値・アプリソースの保管を分離できているか確認する。拡張子の拒否や文字列prefixの比較だけで境界が成立したとしない。任意書込みがある場合はINJ-08/S1とCTR-05/S1で、保存先の実行handlerと、通常の配信主体がアプリ・plugin・起動設定を書き換えられる権限を追い、承認済み更新経路との区別を確認する。[OWASP File Upload](https://cheatsheetseries.owasp.org/cheatsheets/File_Upload_Cheat_Sheet.html)
3. **URL取得がある場合は接続処理まで追う。** 許可するscheme・宛先、解決したIPv4/IPv6、redirect・retry時の検証と実際の接続先、不要な内部・metadata宛てのegressを確認する。URL検証helperだけを全呼出元の安全性へ広げない。監査中にDNSや対象URLへ接続して試さない。資料中の「内部ファイルを取得」という説明だけからSSRFの成立を断定しない。[OWASP SSRF Prevention](https://cheatsheetseries.owasp.org/cheatsheets/Server_Side_Request_Forgery_Prevention_Cheat_Sheet.html)
4. **サービス用の鍵と利用者権限を照合する。** 共通鍵を知るだけで任意の利用者IDへログインできる分岐、別サービス・別用途への鍵の使い回し、広域の読取・管理・送信権限を追う。サービス主体の認証と、利用者/tenantの認証・認可を分けて記録する。失敗計数・ロックアウト悪用・既発行sessionの失効も既存条件で確認する。認証・認可の拒否ケースはTST-02/S1でテスト定義を読むが実行しない。秘密値は記録・外部照合しない。
5. **メール生成以外の送信権限も読む。** 固定テンプレートの通知APIに加え、同じworkloadや鍵から直接使えるSMTP/API、queue、別workerの経路を確認する。通知本文の制限と、侵害した主体による送信権限の濫用はそれぞれ根拠を残す。サービス/主体別の送信量、拒否・成功・設定変更の監視定義を担当と停止・失効判断へ結ぶ。本文・秘密鍵・全宛先のログ記録は求めない。詳細は[メールの確認手順](mail-notification-review.md)。

## 封じ込め・復旧資料の読み方

侵入経路の修正、残存プログラムの除去、資格情報の失効、信頼できる環境への復旧は、別の完了条件として記録する。既存IR項目への当てはめは本スキルの防御設計であり、下記指針の逐語的チェックリストではない。[NIST SP 800-61r3、RS.MI・RC.RP](https://nvlpubs.nist.gov/nistpubs/SpecialPublications/NIST.SP.800-61r3.pdf)

- **保全と調査範囲。** 隔離・変更前後の証拠をどこで取得し、時刻・timezone・取得元・hash・取扱者を残すか読む。コード、plugin、起動設定、定期実行、管理アカウント、配布物、設定、DB変更など、調査対象と承認済み基準の対応を確認する。repo内の差分だけで実サーバーの残存コード不存在を証明しない。
- **鍵交換の依存関係。** 影響し得るサービス鍵・DB資格情報・session/token等と、その利用元・更新順序・拒否確認・担当を照合する。連携や非同期workerへの影響、停止時の代替機能、再開の承認条件を手順へ対応付ける。交換日だけで旧値・既存sessionの失効を確認したとは扱わない。
- **再開の根拠。** 復元元の来歴と完全性、設定・データの整合、必要な業務連携、再開後の監視を、提供された記録の範囲で区別する。LLMやスキャナーによるレビューの実施宣言だけで安全性を認定しない。

staticで評価するのは該当するソース・設定・IR-05の保全手順等。SEC-10、IR-02、IR-03、IR-06、IR-07は従来どおりOUT_OF_SCOPEであり、手順書があるだけで実際の失効・残存除去・復元をPASSにしない。fullも別途認可された証拠を受け取るだけで、この手順は実環境操作を許可しない。

## 判定と記録

根拠artifactには、条件ID、snapshot、ファイル/行、入力から到達先までの経路、阻止点、未提供のadapter/設定を記録する。仮説、コードから確認できた不備、実環境未確認を区別する。経路や適用条件が欠ければBLOCKED/REVIEW等に残し、字句一致・無検出・公表文の安全宣言だけでFAIL/PASSを決めない。機能の非該当は個別の証拠と責任者承認で扱う。

対象コード・依存・テストの起動、外部スキャン、侵入・バックドアの設置/削除、実メール送信、鍵失効、復元・再開操作は行わない。事例原資料はCLIやレポートから読まない。
