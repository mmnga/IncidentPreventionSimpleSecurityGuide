# 自動返信・通知メールの悪用防止

メールを生成・配信する機能がある場合に読む。既存220 IDを維持し、HTML/MIMEの出力制御と、通知の内容・送信権限の濫用を別の条件として確認する。変更範囲は [control-update-v9.2.json](control-update-v9.2.json)。個別企業や組織の事例は含めない。

## 担当項目と証拠

| 確認すること | 静的条件 | full条件 |
|---|---|---|
| 外部入力がHTML/CSS・ヘッダー・MIME構造や表示を変更しないか | WEB-01/S2 | WEB-01/MAIL-1 |
| 任意の文章・URLを公式通知として発信できないか、宛先・送信権限・量を制限できるか | WEB-09/S5 | WEB-09/MAIL-1 |

認証・worker認可・最小権限・記録・テスト定義はAUT-01、AZ-01/08、SEC-07、CLD-03、OBS-07、TST-01/02を再利用する。メール送信の存在やDKIM設定だけで不備を確定せず、候補がなくても上記2条件を個別に検証する。

## 静的に追う経路

1. 問い合わせフォーム、受信メール、外部event等の入力から、保存・変換・テンプレートの差し込みまでを追う。本文以外の名前・件名・URL・添付・引用にも注目する。
2. text/plainとHTML版、ヘッダー、MIME境界、添付の構造がどこで決まるかを確認する。raw/safe指定、CSSによる表示の隠蔽、Markdown変換、URLの自動リンク化を確認する。スクリプト禁止やHTMLエスケープだけで、詐欺文面の反射まで防げたと判断しない。
3. 受付→event/queue→宛先解決→通知生成→配信adapter→署名の境界を照合する。固定テンプレート、サーバー生成の受付番号等の限定値、固定用途URLを優先する。外部入力で自由本文・件名・任意URL・生MIMEを指定できる引数や迂回経路を残さない。
4. 宛先の所有確認・用途への拘束と確認前メールの内容、直接呼出し・別API・再試行、資格情報の所在と権限を確認する。共有送信上限、重複抑止、障害時の扱い、異常時の停止判断を既存項目と対応付ける。
5. 各条件のartifactへファイル/行、確認した入力元・各パート/ヘッダー・差し込み値の由来・送信権限を記録する。外部サービス上のテンプレート、署名設定、別repo等が未提供なら、その経路はBLOCKED/NOT_RUN等として残す。

`html`・`text`という引数名や`send`という関数名だけで、メール生成や送信の実挙動を断定しない。adapterが未提供で、下流が値を無加工で使うか、固定テンプレート等で制限するか不明なら、その判断はREVIEW/BLOCKEDに残す。既知の生成APIや提供済みadapterまで追って確認できた不備だけを、確認した境界に限定してFAILとする。実際の署名・配信・表示・再送の成立は別の証拠を必要とする。

原文の引用が業務上必要な場合は、用途・範囲・受信者・信頼表示と同等の悪用防止根拠を確認する。正規ユーザーの必要な通信を一律禁止する条件ではない。解消できない公式通知としての悪用はFAIL、判断資料不足は未確認、承認された残存リスクは既存のWAIVEDで扱い、PASSへ置き換えない。

受付APIと通知サービスを分け、通知側へ自由本文の読取権限を与えない設計は一例。同一プロセスでも、型/schema・呼出し権限・固定テンプレート等で同等の境界を強制できれば評価する。マイクロサービス化の有無だけで合否を決めない。

メール機能がない場合は新しい個別条件ごとに根拠と承認付き非該当を記録する。WEB-01/WEB-09の既存条件をまとめてスキップしない。外部配信サービスの資料がないことも、機能の不存在の証明にはならない。

## DKIM・表示と確認範囲

通常のDKIMは署名対象データの検証であり、本文の安全性やSMTP配送先への拘束を保証しない。署名対象を維持した再送が成立する範囲は残る。DKIM/SPF/DMARCの成功、To等の署名、署名期限、送信上限や宛先確認だけを、この悪用の完全防止としない。DKIMを無効化する対策も求めない。[RFC 6376 §8.6](https://datatracker.ietf.org/doc/html/rfc6376#section-8.6)

正しいtext/plainはHTMLの書式命令を解釈しない。見た目だけからHTML化や署名破壊を断定せず、生成済みメールのContent-Type・multipart構造・署名対象を区別する。[RFC 2046](https://datatracker.ietf.org/doc/html/rfc2046#section-4.1.3)

自動返信への大量の原文引用を避け、不要な内容の中継・増幅を防ぐ方針はRFC 3834を参照する。フォーム、queue、IAMや固定通知APIへの適用は本スキル独自の防御設計で、RFCの公式チェックリストではない。[RFC 3834](https://datatracker.ietf.org/doc/html/rfc3834#section-3.1.1)

staticではソース・宣言的設定・提供済みメール等を読むだけ。対象のメール生成コード・テストの実行、実送信、DNS照会、リプレイ、受信者への接触は行わない。fullも別途認可された隔離環境の生成結果等を証拠として受け取るだけで、CLIは実行しない。実配信・実クライアント表示・運用設定の適用を未確認のままPASSへ含めない。

## 移行

v9.2はstatic 184条件、full 127条件。220 ID / static 172 / OUT_OF_SCOPE 48、schema 3、期限・状態・終了コードは維持する。既存の個別条件は変更せず追加する。台帳とengineの変更でscopeが変わるため、旧証拠のscopeを書き換えず新しい範囲で確認する。旧結果の再表示では元の判定・日時・scopeを保持し、追加条件未確認と明示する。
